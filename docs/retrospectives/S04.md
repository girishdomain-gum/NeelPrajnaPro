## THE RESULT
Built from Appendix B's prose alone, the detector reproduced the previous
era's population **exactly: 3,099 pivots / 465 pools / 325 sweeps** on the
designated 16,029-bar window.

Why this is worth more than a passing test: Appendix B §B.8 admitted its own
weakness — it was written FROM the old code, so any re-derivation from it
could only prove text-code fidelity, never correctness. It stated that true
independence would require a population produced by a genuinely different
implementation. **The Owner's rewrite-from-scratch ruling produced exactly
that.** The previous era could not obtain this confirmation; this one did.

The Developer's own statement of scope, kept verbatim because it is the right
shape for every future claim: it says nothing about whether liquidity sweeps
predict anything — C3 forbids this detector from having an opinion — it says
the mechanics, read only from prose, produce the same population a completely
different codebase produced.

**And it held across a change.** R1 restructured what `detect()` emits (325 →
790 observations). All three numbers were unchanged. A first parity result
could in principle come from code shaped toward the target; one that survives
restructuring the output is a result about the mechanics.

## What went well
1. **M2 designed to fail numerically, not structurally** — a transitive-chain
   bug produces level 100.50 instead of 100.25. A test that distinguishes by
   number is worth ten that distinguish by code path.
2. **B.4 enforced by construction** — a new pool simply is not in `active`
   when the check pass runs, rather than a "skip the pool I just made" guard.
   Same instinct as S02's atomicity: make the bad state unreachable.
3. **Reading rather than skimming the spec** — the Developer noticed that
   every confirmed pivot joins history whether or not it formed a pool, a
   consequence Appendix B implies but never states.
4. **The source disclosure surfaced a risk neither party had considered**
   (see below). That is what disclosure is for.
5. **pyarrow used ephemerally** for a one-off analysis, never added as a
   project dependency.

## What went wrong
- **POOL_FORMED was dropped from the SDK output** and pool counts exposed
  through a side channel outside the interface. Three problems: the definition
  is a two-event chain, so the output was a strict subset of the spec it
  claimed to implement; the judge would lose its denominator (a sweep rate
  needs the pools that never resolved); and the side channel carried no
  provenance, escaping C1 entirely. Fixed in R1.
- **Audit fields were partial** — pool_members, close-back ticks and pool age
  were missing. Fixed in R2, and the timing mattered: adding a field after
  observations exist means every earlier observation lacks it forever.

## Rules this sprint forged
1. **A number the judge needs must be provenance-bound.** If it matters, it
   travels inside the ObservationSet, not beside it.
2. **A parity claim is only true of the code that produced it.** Any change to
   what a detector emits requires re-running parity before the claim stands.
3. **The strength of an independence claim IS the scope of its sources.** That
   scope belongs in the written record, not in memory — and it must include
   what any delegated search touched, not only what was read directly.
