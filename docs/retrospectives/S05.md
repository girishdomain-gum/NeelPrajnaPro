## What was built
The judge — and, more to the point, its ability to acquit. A block-resampling
null, a per-family trial ledger with incremental alpha, an Owner-gated
ceremony, and the Battery: the only thing permitted to write a verdict.
81 tracked files; 106 tests (was 77).

## What went well
1. **The best architectural call of the sprint was a rejection.** A separate
   verdict store with a two-phase write was considered and refused, because
   two stores cannot be atomic against each other without a protocol nobody
   built. Making the verdict a new OP on the window ledger's own RecordStore
   means verdict-and-burn are literally one file append — so S02's atomicity
   proof applies unmodified. That is reuse of an ARGUMENT, not just code.
2. **Alpha constants recorded, not just the rule name.** AM-03 required the
   rule by name; the Developer recorded the name AND both constants. Without
   them, a future change to the ratio would silently reinterpret every
   historical verdict. The migration promise became real rather than nominal.
3. **Refusing to claim more than the code delivered.** "Sole verdict writer"
   was reported honestly as a claim about computation, not access control —
   which is what prompted R1 and made the claim true.
4. **The crash drill was honest from the start** — torn tail and stale lock
   both left behind, no reminder needed. F-02's lesson has become reflex.
5. **The acquittal was demonstrated, not asserted**: the no-effect case
   returned p = 1.0 exactly, with the reason stated (every null draw ties the
   observed).
6. **Knowing where to stop.** R1 was taken to the point where a caller must
   deliberately import a single-purpose class, and no further — stack-frame
   inspection was declined with reasoning: it would break under indirection
   and refactoring, buying an illusion of enforcement at real cost.

## What went wrong
- Nothing failed. One structural gap (R1): the verdict-writing method was
  public, so "the Battery is the sole verdict writer" described current
  callers rather than a property of the code. Fixed with a capability token,
  checked FIRST so a refused call has no side effect at all.

## Rules this sprint forged
1. **A bad state made unreachable beats a bad state documented as unlikely.**
   Third sprint running that this decided a review (S02 atomicity, S04's B.4
   ordering, now the verdict gate).
2. **Record the rule AND its constants.** A rule name alone lets a future
   parameter change silently reinterpret history.
3. **A refusal must have no side effect.** Check the gate before doing work,
   and prove the world is unchanged afterwards — the R1 drill asserts the
   window is still unburned, not merely that an exception was raised.
4. **Know where a fix stops.** Take it to the point where it changes what a
   caller must deliberately do; ceremony beyond that buys illusion.

## Carried forward — an OPEN POLICY QUESTION for the Owner
The geometric alpha schedule halves each registration: alpha_1 = 0.025,
alpha_7 ≈ 0.0004, alpha_10 ≈ 0.00005. The family's capacity is therefore
**100 nominally and roughly 6–8 in practice** — beyond that, the required
resample count is unreachable however much data exists.

This is not a defect: protecting a family total always costs something, and
the Developer named the tension openly in the report and the docstring. But
the Owner chose 100 because he intends families to accumulate hypotheses over
years, and a schedule exhausted after seven is a different thing from what he
asked for.

Deferred deliberately, not forgotten. S06 uses registration #1 at alpha 0.025
and is unaffected. AM-03's migration requirement means any future scheme
applies FORWARD only, so no historical verdict is ever reinterpreted — which
is precisely what makes deferring safe rather than lazy. Options when the
Owner wants them: keep geometric (few, strong tests); a gentler decay (more
usable slots, each weaker); or **alpha-investing**, where a family that keeps
finding real effects earns budget back — the best fit for a long-lived
platform.

## Other limitations carried
- Later registrations need rapidly growing N to remain testable at all.
- `TrialLedger.register()` refuses ANY re-registration of an existing id,
  even byte-identical — stricter than the spec required, chosen over building
  field-by-field diff logic for a case the spec does not ask to distinguish.
- The capability token is not a hard security boundary; Python has none
  across modules. Stated in the class's own docstring.
